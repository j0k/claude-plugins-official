# Issue #57372 — the bug we're bypassing

**Upstream:** https://github.com/anthropics/claude-code/issues/57372

## Symptom

In v0.0.6, the Telegram plugin's MCP tools (`reply`, `react`, `edit_message`, `download_attachment`) silently disappear from Claude Code's tool registry **after 2–5 minutes of session uptime**.

Visible in `claude --debug mcp` logs as:
```
[DEBUG] Dynamic tool loading: 1/46 deferred tools included
   …after ~5 min…
[DEBUG] Dynamic tool loading: 0/42 deferred tools included
[WARN] Filtering out tool_reference for unavailable tool: mcp__plugin_telegram_telegram__reply
[WARN] Filtering out tool_reference for unavailable tool: mcp__plugin_telegram_telegram__react
[WARN] Filtering out tool_reference for unavailable tool: mcp__plugin_telegram_telegram__edit_message
[WARN] Filtering out tool_reference for unavailable tool: mcp__plugin_telegram_telegram__download_attachment
```

The model still tries to call tools, gets `Error: Tool mcp__plugin_telegram_telegram__reply not found`, has no recovery path, falls silent. The user sees the bot stop responding.

## What is NOT in the host logs

This is what makes it hard to diagnose:

- ❌ No `MCP server disconnected`
- ❌ No `Channel deregistered`
- ❌ No `stdin closed` / `process exited`
- ❌ No exception or stack trace at the moment of removal
- ❌ No cache rotation marker
- ❌ No timer firing

Tools just vanish. The plugin process is still alive (heartbeat continues), MCP stdio is still open, but the host has dropped the registrations.

## Differential clue

In the same Claude Code session, with the same stdio transport, a `playwright` MCP server is **unaffected** for hours. The only structural difference:

```
Channel notifications registered: plugin:telegram:telegram   ← affected
Channel notifications skipped: server did not declare claude/channel  ← unaffected
```

→ Bug is scoped to **`claude/channel`-capable stdio MCP servers**, not stdio MCP in general.

## Cadence

Suspiciously close to but not strictly tied to **5 minutes** — the default Anthropic prompt-cache breakpoint TTL. Observed:

- 4m44s
- 5m00s
- ~21 min in a low-activity session

Variable. May be activity-dependent.

## Four hypotheses (unverified, listed by plausibility)

We cannot read Claude Code's source. From observable behavior alone, any of these are consistent:

1. **Cache rotation drops MCP definitions for `claude/channel` servers.** The host caches a prompt prefix containing tool definitions; when that prefix rotates (~5 min TTL), tools fail to re-register specifically for channel-capable servers. The playwright differential supports this.

2. **`claude/channel`-specific timer / watchdog.** A separate host-side lifecycle disables channel servers on its own timer, unrelated to prompt cache. The 5-min match is coincidental.

3. **Periodic cleanup task iterates only channel servers.** A scheduled GC / registry compaction task incorrectly removes them.

4. **Registration race.** `Channel notifications registered` fires twice at startup (e.g. seen at `14:49:47.467Z` and again at `14:49:56.583Z`). A later re-registration may overwrite rather than merge.

## Why we built the architectural bypass instead of waiting for upstream fix

- We have no source access to verify which hypothesis holds.
- All four hypotheses share a common root: the **`claude/channel` code path is buggy**. Removing the plugin from that path makes us immune regardless of mechanism.
- Workaround 4A (periodic `notifications/tools/list_changed` ping) was implemented but didn't reliably prevent the failure.
- A decoupled daemon is independently useful: messages persist across Claude Code restarts, daemon survives `/reload-plugins`, queue files are inspectable.

## The bypass design (v0.1.0)

The new architecture sidesteps the bug by construction:

1. **MCP plugin doesn't declare `claude/channel`.** It only declares `tools` capability. From the host's perspective it's identical to playwright.
2. **Telegram bot runs in a separate daemon process** outside Claude Code's lifecycle.
3. **Communication is via file-based queue** (`inbox/`, `outbox/`), not push notifications.
4. **Wakeup is pull-based** — Claude polls via `read_inbox`, `wait_for_message`, or `/loop 30s /telegram:check`.
5. **15-second ping** (`notifications/tools/list_changed`) remains as defense-in-depth.
